## 原生运行发现并修正的问题

- `/EHsc` 默认将 C linkage 入口视为不抛异常，异常入口现显式使用 `noexcept(false)`。
- JOM 将 `%_PDB%` 转义为包含 `%engine.pdb%` 的引用；CMake 改为显式传目标 PDB 基名。
- 本机 LLVM 子集没有 `llvm-undname`；launcher 增加 DbgHelp 回退并识别本地 lambda 函数拼写。
- 两项工具测试曾假定 POSIX 路径，现保留实际平台路径和可执行文件后缀。

## 限制

这些证据仅证明该 demo 在该工具链/CRT 下的行为，不证明 Palace 或任意插件可用。
未验证 LTO、PCH、modules、sanitizers 或混淆/VM；生产者/消费者混用保护模式或密钥不受支持。

扫描器是清单与指定语料门禁，不是零泄露证明。公开导入/导出、继承结构及普通标签仍可见。
密文可能形成疑似路径。私有文件分类按文件名/包路径启发式处理，改名后可能漏检；不解析 PDB 内容。
保护 PDB 保留链接符号，但缺少被 launcher 移除的源元数据。

### 从二进制到等价函数

1. 在 VM 入口捕获 31 字节运行字节码，记录八次实际分派、寄存器状态及处理器地址。
2. 找到此前静态清单未识别的初始化入口 RVA `0x4a8b0`，核对其机器指令。
   程序使用内嵌的掩码 AES 轮密钥、nonce 和密文初始化字节码。
   脚本仅从发布 PE 提取这些材料，调用 Node 标准库 AES-128-CTR；离线结果与运行时 31 字节完全一致。
   这是 VM 自带的解密材料，不是诊断私钥或 RTTI 命名密钥。
3. 按分派器的位置掩码和映射表解码操作数，结合实际 ALU 分支确认 XOR、乘法、逻辑右移和加法。
   所记录处理器及 ALU 分支的指令字节均逐条对照发布 PE，不能只根据一次输入输出猜公式。
4. 将以下操作组合、代入包装函数内嵌常量，自动生成等价 C++ 表达式。

| 字节码偏移 | 恢复操作 |
| ---: | --- |
| 0 | `local[0] = r0` |
| 3 | `r1 = local[0]` |
| 6 | `r2 = r1 ^ r7` |
| 11 | `r3 = r2 * r8` |
| 16 | `r4 = local[0]` |
| 19 | `r5 = r4 >> r9`，逻辑右移 |
| 24 | `r6 = r3 + r5` |
| 29 | `return r6` |

包装函数给出 `r0 = input`、`r7 = 0x5a827999`、`r8 = 33`、`r9 = 7`，得到：

```cpp
std::uint32_t recovered_token(std::uint32_t input) {
    return ((input ^ 0x5a827999u) * 33u) + (input >> 7u);
}
```

所有运算按无符号 32 位执行，包含溢出回绕。恢复的是计算语义，不是原始变量名、注释或源码排版。
